Input子系统：Platform设备模型
- GPIO按键中断驱动

目标硬件：野火 i.MX6ULL Pro 底板 (MCIMX6Y2CVM08AB / Cortex-A7)

目标内核：Linux 4.1.15 (系统节拍：CONFIG_HZ = 100)

物理引脚：SNVS_TAMPER1 (复用为 GPIO5_IO01，板载按键 SW2)

2. 匹配、Probe 与设备节点生成机制

2.1 驱动与设备绑定调用链

  1. 模块加载时通过 module_platform_driver 展开并调用 platform_driver_register(&key_driver)。
  2. Platform 总线匹配器根据 DTS 中的 compatible 属性（"rkljq,keys"）进行匹配。
  3. 匹配成功后，总线调用驱动的 key_probe(struct platform_device *pdev)。

2.2 Input Core 到用户空间节点的生成

在 input_register_device() 内部执行以下操作：

  1. 将 input_dev 挂入全局双向链表 input_dev_list。
  2. 遍历全局输入处理器链表 input_handler_list（其中包含 evdev_handler）。
  3. evdev_handler 通过位图比对匹配成功，调用 evdev_connect() 分配主设备号 13 与次设备号（64+X）。
  4. 调用 device_add() 触发内核 kobject_uevent，用户态 udev/mdev 守护进程收到通知，自动在 /dev/input/ 下创建字符设备节点 eventX。

3. 硬件电路与设备树 (DTS) 规范深度剖析

3.1 野火 i.MX6ULL SW2 按键硬件电路分析

  • 外设引脚：底板按键 SW2 连接核心板 SNVS_TAMPER1。
  • 复用功能：查阅 imx6ull-pinfunc-snvs.h，该引脚支持复用为 GPIO5_IO01（MX6ULL_PAD_SNVS_TAMPER1__GPIO5_IO01）。
  • 电气特性：SW2 闭合连通 3V3，后端串联 10K 下拉电阻到地。按下为高电平 1，弹起为低电平 0（GPIO_ACTIVE_HIGH）。驱动申请中断必须监听双边沿：IRQF_TRIGGER_RISING | IRQF_TRIGGER_FALLING。

3.2 深度剖析：为什么 GPIO 中断引脚必须放在 &iomuxc_snvs 节点下？

  1. 独立供电与待机唤醒：普通 IOMUXC（基地址 0x020E0000）在低功耗待机时断电以节能；而 iomuxc_snvs（基地址 0x02290000）处于 Always-On（常开）电源域，能充当低功耗唤醒源（Wakeup Source）。
  2. 基地址与相对偏移寻址：宏 MX6ULL_PAD_SNVS_TAMPER1__GPIO5_IO01 定义的电气偏移 0x0050 是专门相对于 0x02290000 的。若错放到普通 &iomuxc 下，驱动会写入 0x020E0000 + 0x0050 = 0x020E0050，导致配置静默失效并引发总线异常。同时若宏误写为 MX6UL_PAD_...，其偏移为旧芯片的 0x02AC，在 SNVS 域内直接越界。

3.3 验证通过的标准设备树代码 (imx6ull-rkljq.dts)

5. 时钟节拍与消抖算法的数学模型

5.1 jiffies 是什么？

  • 直观比喻：内核的“脉搏计数器”，系统开机上电后每隔一个 tick 自增 1。
  • 硬件来源：芯片硬件定时器（GPT / EPIT）产生周期性时钟中断。查阅本地内核配置： CONFIG_HZ=100，表明系统每秒产生 100 次时钟节拍，1 个节拍（1 Tick）严格等于 10 毫秒。
  • 时间换算：msecs_to_jiffies(15) 向上取整为 2 个节拍（20ms）。jiffies + msecs_to_jiffies(15) 表示从当前时间点向后推延 15ms 的绝对时刻。
  • 溢出回绕：32 位系统约 49.7 天溢出归零。内核中严禁使用 < 或 > 比较，必须使用标准宏： time_after(unknown, known) 与 time_before(unknown, known)。

5.2 mod_timer 为什么是按键消抖的灵魂？

机械按键触点在 5~10ms 内会产生密集的反弹跳变（毛刺）：

时刻 t = 0ms:  毛刺 1 跳变 ──► 进入 ISR ──► mod_timer(0ms + 15ms = 15ms)
时刻 t = 2ms:  毛刺 2 跳变 ──► 进入 ISR ──► mod_timer(2ms + 15ms = 17ms)  [引信被推后!]
时刻 t = 4ms:  毛刺 3 跳变 ──► 进入 ISR ──► mod_timer(4ms + 15ms = 19ms)  [引信再次推后!]
时刻 t = 5ms:  毛刺 4 跳变 ──► 进入 ISR ──► mod_timer(5ms + 15ms = 20ms)  [最终锁定 20ms]
-----------------------------------------------------------------------------------------
时刻 5ms ~ 20ms 之间: 触点平稳，无新跳变，定时器安稳倒计时 15ms
时刻 t = 20ms: 定时器真正超时！触发 key_timer_callback()，读取稳态高电平，上报按键按下！

核心结论：mod_timer 动态延后引信，只要机械抖动还在持续，定时器就永远不会超时；只有在完全静止 15ms 后才超时采样，从根本上消除了机械毛刺。

6. 用户空间阻塞 I/O 与事件驱动模型

6.1 应用程序 read() 的底层时序

应用程序调用 read(fd, &ev, sizeof(ev)) 时陷入内核 evdev_read。

  1. 若环形缓冲区为空，内核调用 wait_event_interruptible(client->wait, ...)。
  2. 进程状态被置为 TASK_INTERRUPTIBLE（可中断休眠），移出 CPU 运行队列。
  3. 核心结果：CPU 占用率为 0.0%，彻底避免无意义的死循环轮询。

6.2 input_sync() 的唤醒暗号

当按键在软中断回调中执行 input_sync() 时，内核内部调用 wake_up_interruptible(&client->wait)。 内核调度器瞬间将等待队列中的应用程序标记为就绪状态，在下一个调度周期分配 CPU 时钟片，read() 通过 copy_to_user 取出事件返回应用层。

8. 用户空间原生测试程序实现 (key_test.c)

编写用户层测试程序，保存为 ~/linux-drivers/irq_driver/key_test.c：

#include <stdio.h>
#include <stdlib.h>
#include <unistd.h>
#include <fcntl.h>
#include <linux/input.h>

int main(int argc, char *argv[])
{
    const char *device = "/dev/input/event1";
    int fd, ret;
    struct input_event ev;

    if (argc > 1)
        device = argv[1];

    fd = open(device, O_RDONLY);
    if (fd < 0) {
        perror("open device failed");
        return -1;
    }

    printf("Listening to input events on %s ... (Press Ctrl+C to exit)\n", device);

    while (1) {
        ret = read(fd, &ev, sizeof(ev));
        if (ret < sizeof(ev)) {
            perror("read error");
            break;
        }

        if (ev.type == EV_KEY) {
            printf("[Event] Type: EV_KEY, Code: %d (%s), Value: %d (%s)\n",
                   ev.code,
                   ev.code == KEY_1 ? "KEY_1" : "UNKNOWN",
                   ev.value,
                   ev.value == 1 ? "PRESSED" : (ev.value == 0 ? "RELEASED" : "REPEAT"));
        } else if (ev.type == EV_SYN) {
            printf("[Sync]  SYN_REPORT marker received.\n----------------------------------------\n");
        }
    }

    close(fd);
    return 0;
}

  1. 将 key_irq.ko 与 key_test 拷贝至开发板。
  2. 加载模块：

  3. 查看设备节点与中断：

  4. 运行测试程序监听按键：

    按下 SW2 打印 PRESSED，弹起打印 RELEASED。

10. 常见易错点与防御性编码速查表

序号 经典陷阱 严重后果 标准防御方案
1 remove() 未调用 del_timer_sync 模块卸载后软中断触发，回调访问已释放内存引发 Kernel Panic (UAF) remove() 第一行必须调用 del_timer_sync(&key->timer)
2 在中断上下文调用可睡眠 API 引发调度器崩溃，产生 BUG: scheduling while atomic 严格在进程上下文分配资源，中断顶半部只调用 mod_timer
3 未调用 input_set_capability 声明键值 上报的事件被核心层静默丢弃，应用层读不到任何按键 probe() 中必须明确声明 input_set_capability(dev, EV_KEY, KEY_1)
4 SW2 引脚放在普通 &iomuxc 节点 寄存器基地址偏移错误导致总线异常，且无法在待机时充当唤醒源 必须严格挂在 &iomuxc_snvs 节点下
5 直接使用 GPIO 编号当做中断号传给 request_irq 中断申请失败或申请到错误中断线 必须调用 gpio_to_irq(gpio) 获取虚拟中断号
